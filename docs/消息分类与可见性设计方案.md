# 消息分类与可见性设计方案

> 适用端：网页聊天室（`webchat_room`），QQ 端保持既有行为
> 目标：修复「个人指令回复只有自己能看到」，并建立手动消息 / 自动消息 / 系统播报的可见性模型
> 关联文档：`呈现层设计方案v3_结构化直通.md`、`路线B实现方案_自建聊天室+自定义适配器.md`

---

## 1. 问题定位

### 1.1 现象

玩家在网页聊天室发送指令后：

- 指令回显只有自己能看到；
- 机器人的指令结果也只有自己能看到；
- 自动代理的结算/续接提示反而通过全服横幅广播给所有人。

这与预期正好相反。

### 1.2 根因

| 环节 | 当前实现 | 后果 |
|------|----------|------|
| 前端发送 | `app.js` 的 `sendCmd()` 固定发送 `action:"cmd"`、`private:true`、`req_id` | 所有指令都被标记为私聊 |
| 服务端分流 | `room_server.py` 中 `private = action == "cmd" or bool(data.get("private"))` | `cmd` 被无条件视为私聊 |
| 事件投递 | `webroom_event.py` 的 `_deliver()` 只要存在 `req_id` 就 `send_to_player()` | 指令结果只回给发起者 |
| 自动消息 | `AutoProxyManager._notify()` → `main._send_to_origin()` → `send_by_session()` → `broadcast_broadcast()` | 自动消息进了全服横幅 |
| 战斗长文本 | `combat_handlers.py` 直接 `yield event.plain_result(final_log)` | 网页端可能整段展示回合日志 |

**核心问题：当前只有一个 `private` 布尔值，同时承担了「看板数据不进公屏」和「消息不给别人看」两种语义，缺少消息来源与受众模型。**

---

## 2. 设计目标

1. **手动消息默认公开**：普通聊天、动作类指令的回显与结果进入公屏。
2. **查询类默认私密**：个人信息、储物戒、银行流水等查询结果继续进看板，不进公屏。
3. **自动消息默认私密**：自动代理的结算、续接、失败提示进入个人消息页，不打扰公屏。
4. **用户可配置**：每类消息是否允许他人查看，由用户自己决定，服务端强制执行。
5. **战斗详情默认折叠**：公屏只显示胜负、回合数、剩余气血、奖励等结果，回合日志可展开。
6. **不改游戏核心逻辑**：优先在网页呈现层与消息网关层解决；QQ 端行为不变。

---

## 3. 消息模型

### 3.1 两大来源 + 五种呈现

按用户要求先分「手动 / 自动」两大类，再按呈现细分为五种：

| 大类 | 子类 | 触发方式 | 默认去向 | 默认可见性 | 示例 |
|------|------|----------|----------|------------|------|
| 手动 | 普通聊天 | 输入框发送非指令文本 | 公屏气泡 | 公开 | 「今晚谁有空一起打周本」 |
| 手动 | 动作指令 | 签到、闭关、押镖、突破、购买等 | 公屏气泡 | 公开 | `/签到`、`/突破` |
| 手动 | 查询/看板指令 | 我的信息、储物戒、银行、流水等 | 看板 / 私聊回复 | 仅自己 | `/我的信息`、`/储物戒` |
| 自动 | 自动代理消息 | 自动押镖、宗门任务、灵田、秘境、施肥 | 个人消息页 | 仅自己 | 「自动代理已完成第 3 轮押镖」 |
| 系统 | 全服播报 | 定时 Boss、拍卖会、魔潮、宗门事件 | 顶部横幅 | 公开（锁定） | 「世界 Boss 已刷新」 |

> 说明：查询类之所以默认私密，是因为包含个人资产、背包、银行流水等敏感数据；如果用户坚持公开，可在设置中放开。
> 榜单、秘境列表、仙市行情这类「公共查询」可归入「动作指令」的公开卡片，不涉及个人隐私。

### 3.2 消息信封

所有机器人出站消息统一附带以下字段：

```json
{
  "type": "chat | bot | reply | notice | broadcast",
  "channel": "manual | auto | system",
  "audience": "public | self",
  "actor": "web_某某 / QQ号",
  "req_id": "请求幂等号，可为空",
  "title": "消息标题，可为空",
  "text": "公屏展示文本",
  "summary": "结果摘要，可为空",
  "detail": "可折叠详情，可为空",
  "detail_collapsed": true,
  "cards": [],
  "images": [],
  "options": [],
  "ts": 1730000000
}
```

约定：

| 字段 | 约定 |
|------|------|
| `channel` | 标识消息来源，前端据此配色、分组、决定是否进个人页 |
| `audience` | **由服务端计算，绝不信任前端传值** |
| `actor` | 消息归属玩家；公开消息里用于「仅发起者可操作」判断 |
| `detail` | 仅在该消息允许公开详情时才进入公屏载荷；否则只进个人页/私聊 |
| `req_id` | 公开回复也带回 `req_id`，发起者据此清除等待态，避免重复渲染 |

## 4. 可见性与用户配置

### 4.1 可见性等级

| 等级 | 含义 | 公屏 | 个人消息页 | 他人可见 |
|------|------|------|------------|----------|
| `public` | 公开 | 显示 | 可选留档 | 是 |
| `self` | 仅自己 | 不显示 | 自动消息必进；手动消息可选留档 | 否 |
| `public_summary` | 公开摘要 | 只显示 `summary` | 完整 `detail` | 摘要可见，详情不可见 |
| `public_full` | 公开全文 | 显示摘要 + 可折叠详情 | 完整留档 | 是 |

### 4.2 默认值

| 配置键 | 可选值 | 默认 | 作用 |
|--------|--------|------|------|
| `manual_action_visibility` | `public` / `self` | `public` | 动作指令的回显与结果 |
| `manual_query_visibility` | `self` / `public` | `self` | 查询/看板指令结果 |
| `auto_visibility` | `self` / `public_summary` / `public_full` | `self` | 自动代理消息 |
| `battle_detail_visibility` | `public` / `self` | `public` | 战斗回合详情是否允许他人展开（默认所有人可展开） |
| `battle_detail_default` | `collapsed` / `expanded` | `collapsed` | 战斗详情默认折叠状态 |
| `chat_visibility` | `public` / `self` | `public` | 普通聊天 |

### 4.3 存储位置

建议存放在网页账号库 `webchat_room/accounts.py` 的 `users` 表中，新增一列：

```sql
ALTER TABLE users ADD COLUMN settings TEXT NOT NULL DEFAULT '{}';
```

理由：

- 这是网页端展示偏好，不影响游戏数值；
- 避免改游戏主库、避免新增游戏数据库迁移；
- 与账号绑定关系一致，换设备登录仍然生效。

读取时做一次 JSON 合并，缺失键使用默认值；写入时只更新已知键，避免旧版本字段丢失。

### 4.4 配置入口

在「账号设置」弹层新增「消息可见性」分区：

| 控件 | 说明 |
|------|------|
| 动作指令消息 | 公开（默认） / 仅自己 |
| 查询结果 | 仅自己（默认） / 公开 |
| 自动代理消息 | 仅自己（默认） / 公开摘要 / 公开全文 |
| 战斗详情 | 所有人可展开（默认） / 仅自己可展开 |
| 战斗详情默认状态 | 折叠（默认） / 展开 |
| 恢复默认 | 一键重置 |

保存后立即生效，不需要重新登录。前端只负责展示与提交，真正的过滤在服务端完成。

## 5. 路由与协议

### 5.1 手动指令：新流程

```text
玩家 A 输入 /签到
  → 前端发送 action:"cmd", req_id, panel:false, 可选 one_shot_visibility
  → room_server 计算 audience：
      1. 查询/看板指令 → self
      2. 用户设置 manual_action_visibility=self → self
      3. 其余 → public
  → 若 public：先广播指令回显（type:"chat", channel:"manual", is_cmd:true）
  → 适配器构造事件：req_id、audience、channel="manual"、panel
  → Handler yield 结果
  → WebroomMessageEvent._deliver()：
      audience=self  → send_to_player(type:"reply", req_id)
      audience=public → broadcast_bot_payload(type:"bot", req_id, channel:"manual", actor)
  → 发起者按 req_id 清除等待态并渲染一次；其他玩家直接渲染
```

关键点：

| 问题 | 处理 |
|------|------|
| 发起者重复渲染 | 公开指令不再本地回显，以服务端广播为准；`bot` 载荷带回 `req_id` |
| 看板数据泄露 | `panel:true` 的请求永远走 `reply`，不进入公屏 |
| 他人点击了别人的选项 | 公开消息带 `actor`；前端只对 `actor === 自己` 渲染可点击选项/操作按钮 |
| 撤回 | 指令回显使用服务端 `msg_id`，沿用现有撤回逻辑 |

### 5.2 自动消息：新流程

```text
AutoProxyManager._notify(origin, msg, user_id)
  → notifier(origin, msg, user_id=user_id, channel="auto", category="auto_proxy")
  → main._send_to_origin() 判断 origin 是否 webroom
      ├─ 是 → room_server.notify_player(room_id, player_key, notice)
      │       ├─ 解析 player_key → 网页账号
      │       ├─ 持久化 notice
      │       ├─ 推送给该玩家所有在线连接（type:"notice"）
      │       └─ 若 auto_visibility 允许公开 → 额外广播摘要
      └─ 否 → context.send_message(origin, ...)（QQ 等旧行为）
```

`notify_player` 的职责：

| 步骤 | 说明 |
|------|------|
| 解析账号 | `web_<用户名>` 直接取用户名；绑定 QQ 的按 `users.player_key` 反查 |
| 持久化 | 先写库再推送，保证离线不丢 |
| 推送 | 推给该玩家全部在线连接，而不是只推第一条 |
| 公开策略 | `self` 不广播；`public_summary` 只广播摘要；`public_full` 广播摘要 + 可折叠详情 |
| 去重 | 5 秒内相同标题 + 摘要的重复通知合并，避免自动代理抖动刷屏 |

### 5.3 系统播报

保持不变：

```text
context.send_message(umo, ...)
  → webroom_adapter.send_by_session()
  → room_server.broadcast_broadcast()
  → 前端横幅
```

系统播报不属于个人消息，始终公开，不受用户设置影响。

### 5.4 协议字段变更

客户端 → 服务端：

```json
// 普通聊天
{"action": "msg", "text": "..."}

// 指令
{
  "action": "cmd",
  "text": "/签到",
  "req_id": "r_xxx",
  "panel": false,
  "one_shot_visibility": "public | self | null"
}
```

服务端 → 客户端：

```json
// 公屏指令回显
{"type": "chat", "channel": "manual", "is_cmd": true, "actor": "web_a", "text": "/签到", "msg_id": "..."}

// 公开指令结果
{"type": "bot", "channel": "manual", "audience": "public", "actor": "web_a", "req_id": "r_xxx", "text": "...", "summary": "...", "detail": "", "cards": [], "ts": 0}

// 私密指令结果 / 看板
{"type": "reply", "channel": "manual", "audience": "self", "req_id": "r_xxx", "panel": true, "text": "...", "cards": [], "ts": 0}

// 自动消息（进个人消息页）
{"type": "notice", "channel": "auto", "audience": "self", "notice": {"id": 1, "title": "...", "summary": "...", "detail": "...", "category": "auto_proxy", "is_read": false, "created": 0}}

// 自动消息公开摘要（可选）
{"type": "bot", "channel": "auto", "audience": "public", "actor": "web_a", "summary": "...", "detail": "", "ts": 0}
```

## 6. 个人消息页（收件箱）

### 6.1 交互

| 区域 | 内容 |
|------|------|
| 入口 | 右侧看板新增「消息」Tab，移动端底部新增「消息」导航 |
| 角标 | 未读数，`0` 时隐藏；新通知实时 +1 |
| 列表 | 按日期分组；每条显示分类图标、标题、摘要、时间、未读点 |
| 展开 | 点击条目展开详情；详情默认折叠；展开即标记已读 |
| 筛选 | 全部 / 未读 / 自动代理 |
| 批量 | 全部已读、清空已读 |
| 操作 | 从详情中提取可点击指令（复用 `extract_options`），仅本人可点 |

### 6.2 数据表

在 `webchat_room/accounts.py` 的 `accounts.db` 中新增：

```sql
CREATE TABLE IF NOT EXISTS webroom_notices (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    username    TEXT NOT NULL,
    player_key  TEXT NOT NULL DEFAULT '',
    channel     TEXT NOT NULL DEFAULT 'auto',
    category    TEXT NOT NULL DEFAULT 'auto_proxy',
    title       TEXT NOT NULL DEFAULT '',
    summary     TEXT NOT NULL DEFAULT '',
    detail      TEXT NOT NULL DEFAULT '',
    payload     TEXT NOT NULL DEFAULT '{}',
    created     INTEGER NOT NULL,
    is_read     INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX IF NOT EXISTS idx_notices_user_time
    ON webroom_notices(username, created DESC);
```

保留策略：

- 每个账号最多保留最近 200 条；
- 超过 30 天的自动清理；
- 清空只删已读，避免误删未读。

### 6.3 接口

| 方法 | 路径 | 用途 |
|------|------|------|
| GET | `/api/notices?before=&limit=&unread_only=` | 分页拉取通知与未读数 |
| POST | `/api/notices/read` | `{ids:[...]}` 或 `{all:true}` |
| POST | `/api/notices/clear` | 清空已读 |
| WS | `{"action":"inbox","op":"list|read|clear"}` | 实时同步的可选实现 |

建议：**列表走 HTTP，实时新消息走 WebSocket**。HTTP 便于分页和刷新，WS 只负责推送。

## 7. 战斗详情折叠

### 7.1 识别位置

在 `webchat_room/text_struct.py` 新增 `parse_battle(raw)`，在 `_deliver()` 中优先于 `parse_text()`：

```python
parsed = parse_battle(text) or parse_text(text)
```

不在每个 Handler 里改 `yield`，避免影响 QQ 端与游戏逻辑。

### 7.2 识别规则

| 特征 | 说明 |
|------|------|
| `☆━━━━ 战斗开始 ━━━━☆` | 战斗头 |
| `-- 第 N 回合 --` | 回合块 |
| `☆━━━━ 战斗结束 ━━━━☆` | 结果头 |
| `🏆 ... 获胜 / 平局 / 结束` | 结果行 |
| `战斗 / 切磋 / 决斗 / 挑战` + `回合` | 兜底识别 |

### 7.3 结构化结果

```json
{
  "id": "battle_xxx",
  "kind": "battle",
  "title": "战斗结果",
  "summary": [
    ["胜者", "某某"],
    ["回合数", "5"],
    ["剩余气血", "62% vs 38%"],
    ["奖励", "修为 +500"]
  ],
  "detail": "完整回合日志……",
  "detail_collapsed": true,
  "raw": "原始全文"
}
```

前端渲染：

- 默认只显示 `summary`（结果、胜者、回合数、剩余气血、奖励）；
- 提供「展开战报 / 收起战报」按钮；
- **默认所有人可展开**：公开载荷照常携带 `detail`，只是初始状态为折叠；
- `battle_detail_default=expanded` 时默认展开；
- 仅当用户把 `battle_detail_visibility` 改成 `self` 时，公开载荷才剥离 `detail`，详情改走私聊 `notice`。

### 7.4 覆盖范围

| 场景 | 输出位置 | 处理 |
|------|----------|------|
| 切磋 / 决斗 | `combat_handlers.py` | 结果公开，回合折叠 |
| 团本 / 世界 Boss / 周本 | 对应 handlers | 同上 |
| 劫镖 / 江湖事件 | `robbery_handlers.py` 等 | 同上 |
| 自动代理秘境战报 | `AutoProxyManager` 通知 | 个人页内折叠 |

## 9. 分阶段实施与验收

| 阶段 | 内容 | 验收标准 |
|------|------|----------|
| P0 | 消息信封 + 指令分类 + 手动公开 | A 发 `/签到`，B 能看到指令回显与结果；A 发 `/我的信息`，只有 A 看到看板 |
| P1 | 自动消息收件箱 | A 开自动代理，B 看不到自动提示；A 在「消息」页能看到；退出重登后历史还在；未读角标正确 |
| P2 | 用户可见性设置 | A 设「动作指令仅自己」后 B 看不到；A 设「自动消息公开摘要」后 B 只看到摘要，看不到详情 |
| P3 | 战斗详情折叠 | 公屏只显示结果；「展开战报」可查看回合；刷新后默认仍折叠 |
| P4 | 兼容与收尾 | QQ 行为不变；30 天/200 条清理生效；README、metadata、帮助版本同步 |

## 10. 边界与风险

| 风险 | 处理 |
|------|------|
| 发起者看到两条相同结果 | 公屏指令取消本地回显；公开 `bot` 带 `req_id`，前端按 `req_id` 清等待态 |
| 公开消息里的按钮被他人误点 | 载荷带 `actor`，前端只对本人启用；或把 options 走私聊旁路 |
| 看板数据误入公屏 | `panel:true` 强制 `self`，服务端兜底 |
| 自动消息离线丢失 | 先落库再推送 |
| 多设备未读数不同步 | `send_to_player` 改为推给该玩家全部连接 |
| 自动代理短时间重复通知 | 5 秒内相同摘要去重 |
| 公开详情泄露隐私 | 自动消息默认 `auto_visibility=self`；战斗详情默认公开但折叠，用户可改为 `battle_detail_visibility=self` 后剥离 `detail` |
| 绑定/解绑 QQ 后找不到历史 | 通知按 `username` 存，`player_key` 只作索引 |
| 旧前端不传新字段 | 服务端提供默认值，旧字段 `private` 继续兼容 |
| 刷屏 | 摘要截断（建议 120 字）；自动消息不广播详情；系统播报保持横幅 |
