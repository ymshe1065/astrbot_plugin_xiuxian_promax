# 呈现层全命令渲染普查

> 配套文档：《呈现层设计方案 v4：视图契约与全命令改造》
> 本文件只做一件事：**回答「261 条指令的回复，在网页上到底渲染成了什么」**。
> 状态：普查报告（事实底表），不含实施方案；方案在 v4。

---

## 一、结论先行

| 结论 | 数值/证据 |
|---|---|
| 会出卡的指令 | **23 条 / 261（8.8%）** |
| 只有纯文本的指令 | **238 条（91.2%）** |
| **动作回执类**（正确形态就是一句话 + 数值变化） | **134 条（51%）**——这半边本来不需要重布局 |
| **查询与面板类**（真正需要结构化） | **127 条（49%）**——改造火力应全部集中在这里 |
| 文本回复能不能被网页「读懂」，取决于 868 行正则 | `text_struct.py` 610 + `card_sidecar.py` 258 |
| 正则读错的代价不是「丑」，是**错数据 + 假按钮** | `/符箓书` 解析出 3 个点不动的假指令；`/丹方` 的卡片标题变成「130」 |
| 真正被特化解析的伪表格只有 1 类 | `/仙市` 行情（`_parse_market_lines`）；同一个作者写的 `/我的持仓` 就没有 |
| 分组级别的空白 | 宗门 26/26、排行 10/10、钱庄 8/8、飞升 9/9、管理 12/12 **全为纯文本，零卡片** |
| 缺陷分布（可多条） | F1 层级拍平 37、F4 流水 17、F3 多字段 17、F2 伪表格 15、F6 无对比 15、F7 超长 15、F5 选择器 14、F8 假按钮 7、**F9 效果缺位 5**；另有 133 条无缺陷 |

**一句话**：v3 的「结构化直通」实际只覆盖了 23 条出卡指令，且其中 4 条（丹方/丹药配方/符箓书/可制符箓）连卡片都没被正确拆开；剩下 238 条在网页上第一次渲染就是「一段字符串」，之后全靠正则猜。

**补一句更刺眼的**：那 4 条不但拆不开，**连「做出来有什么用」都没写**。
`/符箓书` 35 张符 100% 有 `effects` 配置、0 处展示；`/丹方` 692 条 `desc` 全是「记载XX炼制方法的丹方。」。
而同游戏的 `/丹阁` `/符阁` 商品列表**有** `效果:` 行——「买」看得见，「做」看不见。这条单列为 F9。

**第二个结论同样重要**：**半数指令是动作回执**。`/购买`、`/强化`、`/签到` 这类回复的正确形态本来就是「一句话 + 数值变化」，不需要表格也不需要卡片。改造如果平均用力，就会把一半精力花在本来没病的地方——这也解释了为什么 v4 的 P0 必须按「查询密度」筛，而不是按命令数覆盖。

## 二、方法与可复跑

```bash
python scripts/audit_render.py           # 通道 + 文本形态特征 → docs/_render_audit.json
python scripts/gen_render_table.py       # 缺陷码 / 目标块 / 优先级 → 第八章表格
```

`audit_render.py` 用 AST 解析 `main.py` 的 261 个 `@filter.command`，再沿委派链（`self.xxx_handlers.handle_yyy` / `self._run_zzz`）找到真正产出消息的函数，判定它是否 `plain_result` / `image_result` / `payload_extra`。`gen_render_table.py` 只做规则映射（动作动词表、排行榜后缀、逐条覆盖面），改规则即可重出表，避免表格与结论脱节。

**通道判定（可靠，脚本给出）**

| 通道 | 判定条件 | 网页实际走的代码 |
|---|---|---|
| `文本` | 只出现 `event.plain_result(...)` | `webroom_event.py:126` → `parse_text()` |
| `卡片↓文本` | 出现 `render_card_async` / `image_result`，同时保留文本降级 | `card_sidecar.load_card_for_image()` → `renderCard()` |
| `看板面板` | 命中 `visibility.PANEL_COMMANDS` | 看板固定两格（我的信息 / 储物戒） |
| `结构化` | 出参带 `payload_extra=` | `groups`/`facets` → `renderGroups()` |

**形态判定（不可靠，仅用于分桶）**：脚本会合并命令及其委派函数的字符串模板，统计分隔线、`【】`、键值行、要点行等特征。它衡量的是**模板体量**，不是**单次回复行数**（例如 `/我的信息` 的 833 行是所有分支的并集）。所以本报告不把脚本的 `lines` 当结论，只把它当「这条命令大概长什么样」的线索；凡进入第六、七节的具体判断，都另有抽样实测或源码引证。

### 3.4 动作回执 vs 查询面板

把 261 条按「回复的用途」再切一刀，得到的分布比通道分布更有决策价值：

| 类型 | 条数 | 正确形态 | 现状态 | 是否要改 |
|---|---|---|---|---|
| 动作回执（购买/强化/签到/加入/领取…） | **134** | `note`（+`stats` 展示变化） | 一行气泡或一段长提示 | 大多**不用改**；只有 15 条需要 `stats(delta)` |
| 查询与面板（我的X / X信息 / X列表 / 榜单 / 商店） | **127** | `stats`/`table`/`entries`/`shelf`/`recipe` | 长文本，靠正则猜 | **主战场** |

判定口径：目标块为 `note` / `note + stats` 的记为动作回执（见第八章表格）。

这个 50/50 的切分说明两件事：

1. **不能再按「命令数」估工作量**。261 条听起来要全改，实际只需改 127 条，其中 P0 只有 27 条；
2. **动作回执的价值不在布局，在反馈**。`/强化` 的真正问题是「成功 +1」看不出强化前后差多少，所以要 `stats(delta)` + 光效，而**不是**给它做一张卡片。

## 四、文本通道的六道门槛

`parse_text()` 不是「解析器」，是一组**过不了就整段放弃**的开关。它的判定顺序与硬门槛如下（`webchat_room/text_struct.py`）：

| # | 门槛 | 代码 | 后果 |
|---|---|---|---|
| 1 | 少于 3 行 → 不解析 | `if len(lines) < 3: return None` (L308) | 动作反馈类永远保持气泡，**这是对的** |
| 2 | 必须命中「分隔线 / 记录头 / ≥3 个键值」之一才结构化 | `structured = has_divider or records or kv_count >= 3` (L389) | 纯要点列表、纯流水、纯段落**全部放弃** |
| 3 | 键值标签不能含空格、括号、常见标点，且 ≤18 字 | `_KV = ^([^\s：:，,。、（）()\[\]【】]{1,18})\s*[：:]` (L28) | 「突破成功率（含丹药）」这类标签直接被当普通行 |
| 4 | 要点行必须**行首**就是 `·`/`•` | `app.js::renderSection` 的 `/^[·•]\s*\S/` | 代码里有 **46 处** `f"  · …"` 缩进要点模板，全部不进要点分支 |
| 5 | `[xxx]` **一律**当记录头 | `_RECORD = ^[【\[]([^】\]]{1,30})[】\]]\s*(.*)$` (L24) | `[130]`、`[1]`、`[2]` 被当成标题 → 卡片标题变成数字 |
| 6 | 没有时间轴、没有表格、没有进度条 | 除 `/仙市` 与战报外无特化 | 流水、排行、进度型信息只能拍成文字行 |

**门槛 5 是隐藏最深的一条**：`[130] 回春散·凡方` 本意是「编号 + 名称」，解析器读成「标题=130，副标题=回春散·凡方」。

## 五、抽样实测：文本 → 解析产物

以下为**实际调用 `parse_text()` 得到的产物**（非推测），输入取自各指令的真实模板。

### 5.1 `/符箓书`（最坏）

输入（截取）：

```
🖌️ 符箓书 · 可绘制符箓
━━━━━━━━━━━━━━━
【攻击】
· 烈焰符（凡品）
  成功率 90%｜工费 240/张｜可堆叠
  材料：凡品矿材 0/1（缺1）、凡品灵植 0/1（缺1）
  ❌ 材料不足，当前画不了
【防御】
…
```

产物：

```jsonc
{
  "kind": "list",
  "items": [
    { "title": "攻击", "meta": "",
      "rows": [["材料", "凡品矿材 0/1（缺1）、凡品灵植 0/1（缺1）"]],
      "lines": ["· 烈焰符（凡品）", "  成功率 90%｜工费 240/张｜可堆叠", "  ❌ 材料不足，当前画不了"] },
    { "title": "防御", ... }
  ],
  "actions": [
    { "label": "张｜可堆叠", "cmd": "/张｜可堆叠" },
    { "label": "1（缺1",   "cmd": "/1（缺1" },
    { "label": "2（缺2",   "cmd": "/2（缺2" }
  ]
}
```

三处崩坏：

1. `【攻击】` 被当成**一条记录**，整类符箓降级成它的 3 行正文；
2. 「成功率 / 工费 / 材料」三行平铺，缩进丢失；
3. **三个假按钮**——`240/张` 里的 `/张`、`0/1（缺1` 里的 `/1（缺1` 被当成指令，玩家点了没反应。

**第四处、也是最要命的一处：这张符画出来能干什么，页面上一个字都没有。**

同一份配置、同一个 `TalismanManager`、同一个 `get_talisman_profile()`，`/符箓`（图鉴）是这么写的：

| 符 | `/符箓` 图鉴已输出的效果 | `/符箓书` 显示的效果 |
|---|---|---|
| 烈焰符 | `物伤/法伤+28%；暴击+12%`｜15 分钟 / 生效 3 次 | **无** |
| 金刚符 | `双防+33%`｜30 分钟 / 生效 6 次 | **无** |
| 回春符 | `立即恢复 30% 气血/灵气`｜15 分钟 / 生效 3 次 | **无** |
| 聚灵符 | `炼丹成功率+12%；避劫（可保全劫数≤4的丹药）` | **无** |

`build_craft_book()` 只取了 `rank / success_rate / gold_cost / materials` 四个字段，
`profile["description"]`、`profile["duration"]`、`profile["uses"]` 一个都没用。
这不是「数据缺失」，是**同一份数据在两个相邻页面上一个显示、一个不显示**。

### 5.2 `/丹方`

```jsonc
{
  "kind": "list",
  "items": [
    { "title": "130", "meta": "回春散·凡方（可炼制，成功率 80%）",
      "rows": [["材料", "凡品灵植x1(缺1)、灵石x100(✓)"]] },
    { "title": "131", "meta": "聚灵散·凡方（可炼制，成功率 80%）", ... }
  ],
  "actions": [ { "label": "学习丹方", "cmd": "/学习丹方" }, { "label": "炼丹", "cmd": "/炼丹" } ]
}
```

卡片标题变成「130」；两个按钮没有参数，点了只会得到用法提示。`footer` 里还残留 `<ID或名称>`、`[次数|all]` 这种模板占位符。

**效果同样全缺，而且比符箓书更麻烦——这里连数据都是坏的。**

| 层 | 现状 | 实测 |
|---|---|---|
| 画面 | 只有 `[ID] 名称（状态 · 成功率）` + 材料 + 灵石 | 0 处效果文案 |
| 配置 | 692 个丹方，`desc` 字段**每一条都是** `记载XX炼制方法的丹方。` | 443 个不同的废话模板 |
| 兜底 | `_generate_pill_desc()` 能把配置翻成 `增加500修为（凡品修为丹）` | **是死代码**：`_normalize_recipe` 里 `if not desc` 才调用，而 692 条全都有 desc |
| 数据 | 249 / 692（36%）的 `output_pill` 能查到效果配置 | 443 个（64%）在 `exp_pills`/`utility_pills`/`pills` 里都查不到 |

所以炼丹这件事，玩家在**消耗材料、承担失败率**之前，能看到的只有「成功率」，
看不到「这东西吃了有什么用」。而 `_generate_pill_desc` 已经写好了，只是被一行优先级判断挡在门外。

### 5.3 `/奇遇选择`（编号选项）

输入：

```
✨【奇遇】山中奇遇
━━━━━━━━━━━━━━━
你遇到一位老者。
  [1] 出手相助
  [2] 视而不见
  [3] 索要报酬
```

产物：`items` = 三个记录，`title` 分别是 `"1" "2" "3"`，`meta` 才是选项文案。网页上是三张标题为「1」「2」「3」的卡片，而且**不可点**——明明是最该做成三个按钮的界面。

同类：`/火候`（`  [1] 猛火急攻 —— …`）、`/切原石`、`/选择灵根`。

### 5.4 `/我的持仓`（伪表格）

```
「 我的持仓 」
━━━━━━━━━━━━━━━
股票
S01 丹阁股        1000股  成本 ¥12,340  市值 ¥13,000  +¥660（+5.3%）
```

产物：`sections[0].lines = ["股票", "S01 丹阁股……"]`——**整行原样保留**。空格在这条字符串里，但 `<div>` 会折叠连续空白，五列挤成一团。`_parse_market_lines` 只认开头 4 行内含 `仙市 · 第N盘` 的文本，持仓没有这个头，所以特化解析器不接。

### 5.5 `/银行流水`（时间序列）

```
📋 银行交易流水（最近15条）
━━━━━━━━━━━━━━━
03-12 14:22 💰 存入 +1,000
03-12 09:10 💸 取出 -500
```

产物：一个 `sections`（3 行 lines）+ 一个键值（当前余额）。网页上是 15 行灰字，金额没有正负色，时间没有分组。**同样是时间序列，战报有 `parse_battle` 特化，流水没有。**

### 5.6 `/境界排行`（少数解析成功的）

```jsonc
{ "kind": "list", "title": "📊 境界排行榜",
  "items": [ { "title": "青云子", "meta": "#1",
               "rows": [["境界","筑基期三层"],["修为","8,420/12,000"]] } ] }
```

这条基本正确——但名次被塞进 `meta:"#1"` 这种字符串约定里，网页无法据此排序、无法高亮「自己」、也无法把 10 条排成带表头的表格。**「能解析」和「能渲染」是两件事。**

**优先级判断**：F8 与 F9 并列最严重，但坏的方向不同——

- **F8 是「骗」**：给玩家一个点了没反应的按钮，直接损害信任；
- **F9 是「瞒」**：让玩家在花掉材料和灵石之后才知道这炉丹有什么用。它比「不好看」严重得多，
  因为 F1–F7 都是**信息在、只是排版崩**，F9 是**信息不在**——排版再好也救不回来。

其次是 F5（该点的地方不能点）与 F1（错层级）。F3/F4 属于「能用但难用」。

> 注：F9 是本次补入的第九类。它不属于 F1–F8 任何一类：
> F1 是「有层级但被拍平」，F9 是「这个字段根本没进画面」。两者的修复方式完全不同——
> 前者改渲染，后者必须先补 builder 的数据来源。

**一个反向证据，说明 F9 是遗漏而不是设计取舍**：四个阁的商品列表**是有效果行的**。
`core/shop_manager.py::format_pavilion_display()` 第 1467 行：

```python
effect_desc = '；'.join(self.get_trade_details(item))
effect_line = f"\n   效果: {effect_desc}" if effect_desc else ""
```

也就是说：

| 路径 | 效果信息 | 位置 |

同一个游戏、同一批丹药符箓，「花钱买」看得见效果，「攒材料做」看不见。
这不是风格问题，是两条渲染路径里漏了同一步。

## 九、与 v4 的衔接

### 9.1 一个必须先做的判断：先止血，再换架构

v4 的 ViewModel 要改 261 条指令的产出口，周期长。但本普查发现的 **F8（假按钮）与 F5（编号选择器）是三个局部 bug**，不必等架构：

| 补丁 | 位置 | 改法 | 修掉 |
|---|---|---|---|
| P1 指令白名单 | `text_struct._valid_cmd` | 用 `commands.py` 的 248 个 cmd 名 + 别名建白名单，抓不到的一律不生成按钮 | F8 |
| P2 记录头收紧 | `text_struct._RECORD` | `【】` 才算记录头；`[]` 要求标题含非数字且长度 ≥2 | `[130]`/`[1]` 标题变数字 |
| P3 缩进要点 | `app.js::renderSection` + `parse_text` | 允许 `^\s*[·•]`，按缩进深度输出 `level`，前端分级缩进 | 46 处 `  ·` 模板 |

三条都是百行内的改动，可先上线验证，再进入 V1。

### 9.2 优先级重排建议

原 v4 的 P0 是「使用频率 × 信息密度」，本表在此基础上追加 **失效码权重**：

1. **F8/F1 优先**：`/符箓书` `/丹方`（已列为 P0 第一组）；
2. **F5 次之**：`/奇遇选择` `/火候` `/切原石`——改造成本极低（三行 → 三个按钮），体验提升明显；
3. **F4/F2 再次**：`/银行流水` `/我的持仓`（`timeline` / `table` 都是现成块）;
4. 其余按 v4 原清单。

### 9.3 验收口径补充

| 指标 | 现状 | 目标 |
|---|---|---|
| 假指令按钮 | 实测存在（符箓书 3 个） | 0 |
| 编号选项可点率 | 0%（全是文本） | 100%（F5 类） |
| 卡片标题被数字覆盖 | 存在（丹方） | 0 |
| 单次回复可见行数 | 长回复（我的信息 / 周本加入 / 世界Boss）一屏放不下 | 折叠后 ≤ 30 行可见 |

## 附录 B：口径与局限

1. **通道判定是精确的**：只看是否调用 `plain_result` / `image_result` / `payload_extra`，误判只可能来自「动态 getattr 调用」（本项目未使用）。
2. **形态判定是启发式的**：合并全部字符串模板，长短不代表单次回复长度；因此正文结论以抽样实测为准，形态列只用于分桶。
3. **失效码是规则 + 人工覆盖**：`gen_render_table.py` 先按动作动词/榜单后缀/分组默认打码，再对已读过输出的命令逐条覆盖（如 `/符箓书` F1 F8、`/我的持仓` F2）。未逐条运行（261 条需要不同游戏状态），标注为「主要失效形态」而非唯一。
4. **本表不含 QQ 端结论**：QQ 端是文本原生环境，本报告只讨论网页渲染。
