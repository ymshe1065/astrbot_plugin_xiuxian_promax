## 三、根问题：v3 自己写下的那条风险

v3 第四章「风险与待解决」第 3 条原文：

> **语义缺失**：payload 只有 label/value，没有「这是物品/这是进度」的类型标记。先靠启发式（label 关键词 + value 格式），关键卡片（我的信息/储物戒）可在 sections 里可选加 `kind` 字段精确标注

这条在实现里演化成了三处「嗅探」：

1. **前端按中文分区名判断组件类型**
   ```js
   const isBag = /物品清单|物品栏/.test(name) || (card.kind === "bag" && /物品/.test(name));
   const isSlots = /装备栏|装备槽/.test(name);
   ```
   分区名一改，装备栏立刻退化成普通键值行。

2. **商品从文案反解**（`card_sidecar._promote_lines_to_items`）
   ```
   聚灵散·凡 - 246灵石(8.2折) · 库存3
   ```
   必须命中「有 ` - `」「有『库存』」「价格正则」三条才认作商品。改一次文案，货架就散架。

3. **按钮从文字里正则抓**（`text_struct._extract_actions`、`app.js::extractLineCmd`）
   玩家能点「购买」，是因为文字里恰好写了 `/购买 聚灵散`。

**共同根源**：后端交出去的是排版结果，前端只能倒推语义。v4 要把这条链路正过来。

## 四、v4 核心：视图契约（ViewModel）

### 4.1 一条指令，一份数据，两种渲染

```
                    ┌────────────────────────────┐
   指令 handler ──▶ │ build_view(player, ...)    │  只算数据，不排版
                    └─────────────┬──────────────┘
                                  │ ViewModel (dict)
                 ┌────────────────┴─────────────────┐
                 ▼                                  ▼
      ┌────────────────────┐             ┌────────────────────┐
      │ render_text(vm)    │             │ 消息字段 view      │
      │ QQ 文本 / 卡片图    │             │ webchat 前端渲染    │
      └────────────────────┘             └────────────────────┘
```

- **旧路径保留**：没有 `view` 的指令照旧出文本，走 `parse_text`，行为不变。
- **图片卡保留**：QQ 端继续出图（玩家习惯），网页端优先读 `view`，读不到再读 sidecar。
- **通道 C 收敛**：`fate_shop` / `proxy` 两个专用面板并入契约（`type: "fate_shop" / "proxy"`），写操作接口保留。

### 4.2 契约

```jsonc
{
  "v": 1,                          // 协议版本
  "type": "breakthrough",          // 视图类型 → 前端布局
  "id": "breakthrough_info",       // 稳定标识，用于局部刷新/缓存
  "title": "突破信息",
  "subtitle": "筑基期三层 → 筑基期四层",
  "tone": "gold",
  "blocks": [ /* 原子块，见 4.3 */ ],
  "actions": [
    { "label": "突破", "cmd": "/突破", "tone": "primary" },
    { "label": "去丹阁", "cmd": "/丹阁 丹药" }
  ],
  "footer": "失败会损失 10% 修为",
  "meta": { "refresh": "on_action" }
}
```

三条硬约束：

1. **后端不产 HTML**——避免注入，也避免主题分裂。
2. **不出现排版字符**——builder 里禁止 `\n`、`━━`、`　` 缩进。
3. **单位与精度在 builder 内定死**——前端不做 `toFixed` 猜精度。

### 4.3 原子块（13 种，替代自由形态的 sections）

| block | 数据形状 | 网页表现 | QQ 文本回落 | 典型信息 |
|---|---|---|---|---|
| `stats` | `[{label, value, unit, delta, tone}]` | 指标卡一排 | `标签：值单位` | 灵石、战力、贡献 |
| `progress` | `{label, value, max, text, tone}` | 进度条 | `修为：8,420 / 12,000（70.2%）` | 修为、容量、建筑 |
| `kv` | `{title, rows, collapsible}` | 键值网格（可折叠） | 原键值行 | 属性页 |
| `table` | `{columns, rows, sortable, highlight}` | 表格（排序、涨跌色） | 前 10 行 + 条数 | 排行、持仓、成员 |
| `items` | `{items, selectable, actions}` | 物品网格 | `名称 ×数量` | 背包、仓库 |
| `slots` | `{slots:[{key,label,item}]}` | 装备槽 4×2 | `武器：青锋剑` | 我的装备 |
| `shelf` | `{groups:[{name, items:[{name,price,stock,cmd}]}]}` | 货架网格 | `名称 - 价格 · 库存` | 丹阁/符阁/器阁/百宝阁 |
| `entries` | `{groups, facets}` | 可筛选列表 | 分组列表 | 秘境、历练、悬赏 |
| `timeline` | `{events:[{time,text,tone}]}` | 时间轴 | `时间 文本` | 流水、战报 |
| `chart` | `{kind:"line"\|"candle", series, labels}` | 折线 / K 线 | 最高/最低/涨跌 | 行情、净值 |
| `compare` | `{options:[{label,rate,note,highlight}]}` | 方案对比条 | `A 55% ｜ B 63%` | 破境丹、装备 |
| `recipe` | `{kind, output, effect, craftable, success_rate, cost, materials[], gates[], fire[]}` | 配方卡（产出效果 + 闸门 + 可做 N 次） | `名称（品阶）` + 成功率/工费 + 材料行 + 可做/卡点 | 丹方、符箓书、符箓配方 |
| `note` | `{text, tone}` | 提示条 | 原提示行 | 说明、警告 |

**除 `recipe` 外，新增需求优先组合原有 12 种，确实不够再加。** 块的数量是这套方案能被维护住的前提。

> **唯一的例外：`recipe`。** 计划外新增的第 13 种，理由是现有 12 种没有一种能正确表达「一张配方」：
> - 塞成 `shelf` 不成立——货架是「同质的可买商品」，有价格和库存；配方是同质的可**做**对象，有产出、材料缺口和三道闸门（材料/灵石/格位），没有价格也没有库存；
> - 塞成 `items` 不成立——`items` 假设每件东西结构相同（名称 + 数量），而配方带 1 个产出 + N 个材料 + N 道闸门 + 火候三档，是一棵两层树；
> - 塞成 `table` 不成立——列不固定（材料条数随配方变），而且真正要表达的是「差什么、差多少、能不能做」，不是可排序的行列。
>
> 强行组合的结果就是现在的样子：全部拍平成一串 `lines`。所以破例加第 13 种，**并在此封口，不再接受第 14 种**。

### 4.3.1 `recipe.effect` 是必填字段，不是装饰

配方卡的唯一用途是「决定做不做」。而「做不做」由三件事决定：能不能做（闸门）、做了值不值（**产出效果**）、成本多少。
现状只给了第一和第三，第二项整块缺席——这是 F9（见普查报告第六章）。

```jsonc
"effect": {
  "text": "物伤/法伤+35%；暴击+14%",     // 唯一必填项，人类可读
  "scope": "time",                       // time | run（历练/秘境按次数）
  "duration": { "minutes": 20, "text": "20 分钟" },
  "uses": 4,
  "source": "config",                    // config | derived | missing
  "by_quality": null                     // 丹药专用，见下
}
```

三条硬规则：

1. **`source="missing"` 时必须显式渲染「效果未录入」，不能留白。**
   留白会让玩家以为这东西没效果；`/丹方` 有 443 / 692 条正是这种情况（数据层没有效果配置）。
   宁可显示一句难看的 `⚠️ 效果未录入`，也不能沉默——沉默等于骗。
2. **`by_quality` 存在时，效果是区间不是定值。** 丹药品质倍率为
   `一般 1.0 / 良好 1.15 / 极佳 1.35 / 大师 1.6`（`config/pill_quality.json::effect_multiplier`），
   所以「增加 500 修为」实际是 500～800。只写 500 是错的，写区间才对（`500 ~ 800`）。
3. **`scope="run"` 时不显示时长，改显示次数。** 探索/秘境类符箓按「生效 N 次历练」结算，
   写「持续 15 分钟」会误导（15 分钟根本覆盖不了一次 30 分钟的秘境）。

`render_text(vm)` 对这三条的处理：`text` 原样输出成新行，会破坏 QQ 端逐字一致。
所以文本渲染器的策略是——`effect` 行**只在网页渲染，文本通道丢弃**，并在 V1 的视图测试里
断言「加 `effect` 前后 `render_text()` 输出逐字节相同」（见 §9.5 第 6 条）。

> **✅ 落地进度 · v3.45.13**：三条规则已在**文本层**先跑通，ViewModel 化仍待 V1。
>
> | 规则 | 实现位置 | 状态 |
> |---|---|---|
> | 规则 1（missing 必须显式） | `AlchemyManager._GENERIC_DESC_RE` + `DESC_MISSING`，展示为 `⚠️ 效果未录入` | ✅ 443 条已标注 |
> | 规则 2（区间） | `AlchemyManager._quality_cap()` 从 `pill_quality.json` 取上界，`_generate_pill_desc()` 输出 `500~800` | ✅ |
> | 规则 3（run 按次数） | `TalismanManager.effect_summary()`：`run_scoped` 时写「生效 3 次（历练·秘境）」 | ✅ |
>
> 同时 `source="derived"` 这条链路被真正打通：692 条丹方的 `desc` 原本全是占位文案，
> `_generate_pill_desc()` 是死代码；现在识别占位/套话后重算，249 条拿到真实效果。
>
> **尚未做**（留给 V1/V2）：`by_quality` 只给了区间文本，没有分档明细；
> `effect` 仍是拼好的字符串而非结构字段；火候三连与效果区间的联动也还没接。
> 也就是说 §5 案例里的「点猛火 → 效果区间收窄」目前还不会发生。


### 4.4 与 v3 sections 的映射

| v3 现状 | v4 |
|---|---|
| `sections: [{name, rows, lines}]` | `blocks: [{type, ...}]`，语义显式 |
| 前端按 `name` 正则判断组件 | 按 `block.type` 分发 |
| `entries` 字段（仅储物戒） | 统一为 `items` 块 |
| `groups/facets`（仅秘境/历练） | 统一为 `entries` 块 |
| `actions` 从文本抓 | 显式 `actions` |

**迁移策略：`sections` 不删，作为 `kv` + `lines` 的降级形态保留**，未改造指令继续走。

## 五、案例：先改最坏的两条

挑案例的标准不是「行数多」，而是**「玩家看完这一屏，下一步该干什么，界面有没有告诉他」**。按这个标准，最坏的不是长文本，而是 `/符箓书` 与 `/丹方` 这两条。

### 5.1 为什么这两条最坏

它们同时踩了四个坑，且互相放大：

1. **产出效果整块缺席**——玩家不知道这炉丹、这张符做出来干什么用（F9）；
2. **决策被埋进长句**——成功率、工费、可做张数、卡点在不在，全在缩进文本里；
3. **卡点不指向动作**——界面告诉你「材料不足」，但不告诉你去买哪一种、差几个、买完能不能做；
4. **层级被抹平**——配方 → 材料 → 状态是三层，落到网页是一层普通文字（缩进被 HTML 折叠）。

第 1 条是这次补进来的，也是唯一「修渲染也救不回来」的一条：前三条改 builder 的输出形态就行，
第 1 条必须先让 builder 去 `get_talisman_profile()` / `_generate_pill_desc()` 把数据取回来。
顺带说明为什么它排在第一位——**「能不能做」只是门槛，「做出来值不值」才是决策**。
一条只答门槛不答值不值的界面，玩家看完还是得去问别人。

更麻烦的是，它们**看起来已经改好了**：有卡片、有 sidecar、`/符箓配方` 的注释还写着「网页端可原生渲染，不再退化成长图」。实际渲染是「卡片框里贴几十行字」。

### 5.2 `/符箓书`：三级嵌套被拍平

**现状（实测）**：10 种已掌握符箓 → 卡片 35 行、文本分支 60 行；全部 35 种掌握则约 120 行，塞进**一个** `sections: [{name: "已掌握符箓", lines}]`。

```
🖌️ 符箓书 · 可绘制符箓
━━━━━━━━━━━━━━━

【攻击】
· 烈焰符（凡品）
  成功率 90%｜工费 240/张｜可堆叠
  材料：凡品矿材 0/1（缺1）、凡品灵植 0/1（缺1）
  ❌ 材料不足，当前画不了
· 紫电符（黄品）
  成功率 58%｜工费 720/张｜可堆叠
  材料：黄品矿材 0/2（缺2）、黄品灵植 0/1（缺1）
  ❌ 材料不足，当前画不了
…（省略 8 种）
已掌握 10 种｜当前可画 0 种、合计 0 份｜熟练度 初学（0/10）
🔒 符图未习得 25 张：星辰符、斩仙符、…
```

**五层信息在网页上的真实归宿**：

| 信息层 | 后端其实有 | QQ 文本 | 网页实际渲染 |
|---|---|---|---|
| 配方 | `name` / `rank` / `category` | `· 紫电符（黄品）` + `【攻击】` | 普通文字，无徽章、不可点 |
| **效果** | `effects`（26 种键）/ `duration` / `uses`，`build_profile()` 已翻成中文 | **无** | **无** |
| 参数 | `success_rate` / `gold_cost` | `  成功率 58%｜工费 720/张｜可堆叠` | 普通文字，缩进丢弃，`可堆叠` 重复 10 次 |
| 材料 | `label` / `have` / `need` | `  材料：黄品矿材 0/2（缺2）…` | 普通文字，缺料不着色 |
| 闸门 | `mat_cap` / `gold_cap` / `slot_cap` / `possible` | `  ❌ 材料不足，当前画不了` | 普通文字，只有结论没有归因 |

**效果那行是这张表里唯一的「两列全空」**——不是渲染不出来，是 `build_craft_book()` 根本没去取。
`get_talisman_profile("紫电符")` 直接就能返回 `物伤/法伤+35%；暴击+14%`，隔壁 `/符箓` 图鉴一直在用。

**sidecar 为什么救不回来**（三条硬证据）：

1. `card_sidecar._looks_like_item_head()` 要求行内有 `\d[\d,]*\s*灵石` **且**（含 ` - ` **或** 含「库存」）。`[攻击] 紫电符（黄品 · 成功率58% · 720灵石/张）` 有数字有灵石，但既无 ` - ` 也无「库存」→ 判定失败，不提升为 `items`；
2. `app.js::renderSection()` 的要点判定是 `^[·•]\s*\S`（行首即 `·`），而材料行是 `   ·`（三个空格）→ 不进 bullet 分支；
3. 落到普通行后走 `textContent`，HTML 折叠连续空白 → 三级缩进全丢，35 行长得一模一样。

### 5.3 `/丹方`：同样的病，数量级更狠

**现状（实测 2 个丹方）**：

```
📜 已学丹方列表
━━━━━━━━━━━━━━━
[130] 回春散·凡方（可炼制，成功率 80%）
   材料：凡品灵植x1(缺1)、灵石x100(✓)
[131] 聚灵散·凡方（可炼制，成功率 80%）
   材料：凡品灵植x1(缺1)、灵石x100(✓)
```

卡片分支是每个丹方 4 行（标题 + 每条材料 + 灵石 + 空行）。`config/pill_recipes.json` 共 **692** 个丹方，中期玩家已学常过百 → **单个 section 400 行以上**。

比符箓书更差的五点：

| 问题 | 具体表现 | 后果 |
|---|---|---|
| **效果完全缺席（最根本）** | 692 条 `desc` 全是 `记载XX炼制方法的丹方。`；`_generate_pill_desc()` 明明能算出 `增加500修为（凡品修为丹）`，却因 `if not desc` 的判断永不执行（死代码） | 玩家花掉材料与灵石之前，不知道这炉丹有什么用；另有 443 / 692 条连效果配置都没有 |
| 无分组 | 只按 `recipe_id` 排序；符箓书起码还按 `【类别】` 分组 | 100 个丹方排成一条直线，找「能炼的」靠眼扫 |
| 灵石混在材料里 | `灵石x100(✓)` 与 `凡品灵植x1(缺1)` 同格式同列 | 分不清「缺的是钱还是货」，而这两件事的下一步动作完全不同 |
| 不展示可用替代物 | 只写「凡品灵植 ×1」，但 `/炼丹` 支持 `品阶类别=材料名` 指定具体材料 | 玩家不知道仓里那堆灵植哪个能用 |
| **火候决策缺失** | 火候三档（猛火 −8% 成功率 / 品质↑、文火 +6% / 品质↓、守中 ±0）完全没出现 | 绝大多数玩家永远按默认守中开炉，主动放弃了「博品质」这条玩法 |

关于第一条，要额外说清一件事：**效果与火候是同一个决策的两面。**
火候影响品质，品质影响效果倍率（`1.0 / 1.15 / 1.35 / 1.6`），
所以「猛火值不值得」这个问题的答案，只在**同时看到效果区间**时才成立。
现在两样都没有，等于这条玩法在界面上根本不存在。

**目标视图**：`recipe` 块 + 火候三档内嵌，不额外加块类型。

两点设计说明：

- **火候做成卡内三连**，不是全局开关。点「猛火」这张卡的成功率就从 80% 变 72%，底部按钮同步变成 `/炼丹 130 猛火 all`。成功率随火候变是纯前端的加减（`rate + rate_bonus`），不需要回后端；

第三点关于 `effect.by_quality`：**它和火候三连必须同时出现在卡上，否则两个都没意义。**
玩家的问题是「猛火 72% 但品质↑ 值不值」，所以要一眼看到
`一般 10% / 大师 16%` 与 `72% 成功率 / 品质权重↑` 并排。只给成功率，火候就没有决策价值；
只给效果区间，玩家不知道拿什么换。这也是为什么 `effect` 在 `recipe` 里是必填而不是可选。

对 443 条查不到效果的丹方，`source="missing"`，卡片上固定输出一行
`⚠️ 效果未录入`——见 §4.3.1 规则 1。这行不好看，但它诚实；留白会让玩家以为这炉丹是废的。

**分页硬需求**：692 个丹方的视图会有几百条 `recipe` 块，必然撞上 32KB 上限。所以 `meta.paging` 不是可选装饰，是这类视图的必需品：默认按 `group` 一页 20 条，超出给「加载更多」按钮调 `/丹方 <类别>` 取下一页。

## 九、技术实现

### 9.1 后端模块

```
core/views/
├── __init__.py        # build_view() 调度 + VERSION
├── schema.py          # stats()/progress()/table()/… 构造函数 + validate_view()
├── registry.py        # view_id -> builder
└── builders/
    ├── recipe_book.py     # 丹方 / 符箓书 / 符箓配方（V1 首个，复用同一 builder）
    ├── breakthrough.py
    ├── player_info.py
    ├── pavilion.py
    ├── warehouse.py
    └── ...
```

`recipe_book.py` 一个 builder 出两种 `kind`（`alchemy` / `talisman`）：闸门集合与文本模板按 `kind` 分支，数据结构完全一致。三条指令共用，避免 `/丹方` 和 `/符箓书` 各写一套。

约定：

- builder 是纯函数（输入 player / 查询结果，输出 dict），不碰事件、不发消息；
- builder 抛异常时，调用方**回退到原文本路径**——不能因为视图层出错让指令不可用；
- 单位、百分比精度、颜色语义（涨红跌绿）在 builder 内定死；
- **效果文案只由 builder 生成，不在前端拼**：符箓走 `core/talisman_rules._describe()`（已存在，26 个键全覆盖），
  丹药走 `alchemy_manager._generate_pill_desc()`（已存在，但要先把 `if not desc` 那行改成「desc 是废话模板时也重新生成」）。
  前端只负责排版，否则同一效果会出现两套措辞。

### 9.2 传输

- 消息事件新增可选字段 `view`，与现有 `card` 并存；
- 网页端优先 `view`，其次 `card`（sidecar），最后 `text`；
- `view` 超过 32KB 时降级为「摘要 + 展开再取」，给仓库这类大列表留后路。

### 9.3 前端

```js
function renderView(vm) {
  if (!vm || (vm.v || 0) > SUPPORTED_VIEW_VERSION) return renderLegacy(vm);
  const box = el("div", "view view-" + vm.type);
  box.appendChild(renderViewHeader(vm));
  (vm.blocks || []).forEach(b => box.appendChild(renderBlock(b)));
  if (vm.actions?.length) box.appendChild(renderActionBar(vm.actions));
  return box;
}

const BLOCKS = { stats, progress, kv, table, items, slots,
                 shelf, entries, timeline, chart, compare, recipe, note };
```

未知 `block.type` → 用 `kv` 通用降级，保证不白屏。

### 9.4 QQ 端文本渲染

`render_text(vm)` 按块回落：

| block | 文本 |
|---|---|
| `stats` | `标签：值单位`，一行一个或两个一行 |
| `progress` | `修为：8,420 / 12,000（70.2%）` |
| `table` | 前 10 行 + 「共 X 条，/xxx 查看全部」 |
| `items` | `名称 ×数量`，超长截断 |
| `compare` | `不用丹药 55% ｜ 上品 63% ｜ 极品 78%` |
| `recipe` | 按 `group` 变化插 `【攻击】`+空行；`· 名（品阶）` / `  成功率 X%｜工费 N/张｜可堆叠` / `  材料：…` / `  ✅可画 N 张` 或 `  ❌ 原因`（`kind=alchemy` 用丹方模板，灵石走材料行格式） |

**这是「一套数据两种排版」成立的关键**，否则网页改完 QQ 就崩。`recipe` 块尤其要注意：它的文本模板必须逐字符复刻现有的 `build_craft_book()` / `get_available_recipes()` 输出，包括那个 `   `（三空格）缩进和 `｜` 全角竖线。

### 9.5 测试策略

1. **Schema 测试**：每个 builder 过 `validate_view()`（必填、类型、范围）。
2. **文本快照**：改造前后 `render_text()` 逐字比对。`recipe` 块的基线直接取现有 `build_craft_book()` / `get_available_recipes()` 的真实返回值，不手写。
3. **降级测试**：未知 type / 超版本 / 坏 block，断言不抛异常且可读。
4. **黄金样本**：`符箓书`、`丹方`、`突破信息`、`丹阁`、`我的持仓` 各存「输入 → 期望 ViewModel」。
5. **闸门一致性（配方组专属，必须有）**：
   - 界面 `craftable` == 实际 `/制符 <符名> <craftable>` 能成功画出的张数；
   - 界面「可炼 N 炉」== `/炼丹 <id> all` 实际炼出的炉数（含灵石与格位限制）；
   - 材料行 `owned/need` 与 `resolve_craft_params` / `_material_count` 同源，不允许各自算一遍。
   这三条是「算得跟结算不一样」的唯一防线，比 schema 测试重要。
6. **效果字段（F9 专属，必须有）**：
   - 对 35 张符 + 有配置的 249 个丹方，断言 `effect.text` 非空且与 `get_talisman_profile()` / `_generate_pill_desc()` 输出一致；
   - 对 443 个无配置丹方，断言 `source == "missing"` **且** 渲染结果里出现「效果未录入」——不许静默留白；
   - 断言加 `effect` 前后 `render_text()` 输出逐字节相同（`effect` 只在网页渲染）。
   第 3 条是这个字段唯一会破「QQ 逐字不变」的风险点，必须测。
