## 一、要解决什么

身外化身（仙缘商店 52 号，60/120/240/480 阶梯价，最多 4 尊）的本意是「多一个分身就能同时多干一件事」。这个语义**已经实现了**：

- 槽位账本统一在 `user_cd`
- 开始/结束活动统一走 `start_activity` / `set_user_free`
- 「还有没有人手」统一由 `player_required` 装饰器判

但「什么算一项活动」这件事没有统一登记处。新增历练、秘境、押镖时，各自去改了枚举、文案、白名单、指令、后台循环、自动代理分派。结果是同一个概念有 9 个副本，且没有编译期或测试能约束它们同步。

**改造的核心不是重构总线，而是给总线配一张活动目录（catalog），让所有上层表从它派生。**

改造后新增一项活动要做的事：

```
写 manager（start / settle / exit）
  + 目录加一条 ActivitySpec
  + main.py 加指令装饰器
  + webchat_room/commands.py 加入网页端菜单（无法派生，必须手写）
= 4 处
```

### 2.4 已复现的缺陷 A：自动代理对同一玩家重复扫描

`data/database_extended.py:688`：

```sql
SELECT ap.*, uc.type AS cd_type, uc.scheduled_time AS cd_scheduled_time
FROM auto_proxy ap
LEFT JOIN user_cd uc ON uc.user_id = ap.user_id
WHERE ap.enabled = 1
ORDER BY ap.updated_at ASC
```

`user_cd` 自 v62 起是 `(user_id, slot)` 联合主键，JOIN 缺 `slot` 条件 → 一个玩家有几个槽位就几行。

实测（1 个玩家 + 5 个槽位）：`list_enabled_auto_proxies()` 返回 **5 行**，`process_due` 对同一玩家串行跑 5 次 `_process_one`。

联表出来的 `cd_type` / `cd_scheduled_time` **无人读取**（`_process_one` 第一行就 `self.get(user_id)` 自己重查）。即这个 JOIN 的唯一效果是放大扫描量，并让施肥/灵田这类周期动作有重复执行、重复推送的机会。

### 2.5 三个死枚举

`RAIDING`(7) / `SECT_BATTLE`(8) / `TRIBULATION`(5) 全仓零使用点。留着不报错，但让人误以为掠夺、宗门大比有槽位管理。

**不建议删除**：如果历史存档里有 `user_cd.type = 5/7/8` 的残留行，删掉枚举会让 `get_name` 落到「忙碌中」，反而比现在更糟。加注释标 `@deprecated` 即可。

## 三、目标设计

### 3.1 分两层：静态目录 + 运行时钩子

不把回调函数塞进模块级常量——那会逼 `utils.py` 在导入期去拿 manager 实例，形成循环依赖。分成两张表：

**静态目录 `core/activity_catalog.py`**（只依赖 `models_extended`）

```python
@dataclass(frozen=True)
class ActivitySpec:
    status: int                       # user_cd.type，唯一身份
    key: str                          # "escort"，与存量 auto_proxy.task_type 对齐
    name: str                         # "押镖"
    exit_commands: tuple = ()         # ("完成押镖", "放弃押镖")，自动进忙碌白名单
    action_commands: tuple = ()       # ("押镖",)，自动进重伤禁行名单
    proxy_mode: str = "none"          # none / config / task，见下
```

**不再保留的字段**（首版有，实际是死字段或会破坏结算）：

| 字段 | 为什么删 |
|---|---|
| `state_text` | 文案唯一定义在 `get_name`，见 3.2；存一份就会重新漂移 |
| `exclusive` | `start_activity` 根本不读它，见 3.7 |
| `settle_owner` / `tick_interval` / `due_mode` | S2 阶段没有任何消费者。等 S4 真接调度器时再加，避免出现「写了但没人读」的字段 |

**`proxy_mode` 三档**（这是 S2 落地时才暴露的问题，首版用 `auto_proxy: bool` 会直接破坏结算）：

| 取值 | 含义 | 进 TASK_STATUS | 当前成员 |
|---|---|---|---|
| `task` | 可作为 `/自动代理 <名称>` 的主任务 | 是 | 押镖、宗门任务 |
| `config` | 靠 `config_json` 里的开关驱动，不是主任务 | **否** | 历练、秘境 |
| `none` | 没有自动代理 | 否 | 闭关、调息 |

如果用布尔 `auto_proxy` 派生 `TASK_STATUS`，历练和秘境会被一并塞进去。而
`AutoProxyManager._active_primary()` 正是遍历 `TASK_STATUS` 去查槽位、逐个结算的
——多出这两项就等于把历练、秘境当成押镖一样每轮重复结算。

**运行时钩子**：插件初始化时绑定结算回调，目录只存描述

```python
# main.py initialize
catalog.bind_tick(UserStatus.ADVENTURING, self._tick_adventure)   # 不是 adventure_mgr.finish_adventure
catalog.bind_tick(UserStatus.EXPLORING,   self._tick_rift)        # 不是 rift_mgr.settle_due
```

绑的是 `main.py` 里的**适配器**，不是 manager 的原方法。原因见 3.8。

### 3.2 依赖方向：`get_name` 是唯一来源（修正首版错误）

首版写「`get_name` 改为查目录」，这与「catalog 只依赖 `models_extended`」互斥：

```
models_extended ──import──> activity_catalog   （catalog 要 UserStatus 才写得出 spec）
activity_catalog ──import──> models_extended   （get_name 要查目录）  ← 环
```

`utils.py` 在模块加载期就会调 `UserStatus.get_name`（`_busy_block_hint` 里），延迟 import 也救不了，只会变成每次调用付一次 import 开销。

**正确方向**：`UserStatus.get_name` 保持唯一来源，目录不存文案。

```python
# activity_catalog.py
def state_text(status: int) -> str:
    """players.state 的展示文案。唯一定义在 UserStatus.get_name。"""
    return UserStatus.get_name(int(status))
```

`ActivitySpec` 因此**不需要 `state_text` 字段**。首版有这个字段，是它把依赖画反了的连带结果。

### 3.3 派生关系

| 原来手写的位置 | 改成 | 备注 |
|---|---|---|
| `_STATE_TEXT` | 从 `UserStatus.get_name` 派生（见 S1a） | 缺陷 B 消失 |
| `BUSY_STATE_ALLOWED_COMMANDS` | **原有手写项原样保留** + 追加 `spec.exit_commands` | 见 3.4，只加不删 |
| `BUSY_BYPASS_COMMANDS` | 原有项保留 + 追加 `spec.exit_commands`（转成 tuple） | 同上 |
| `INJURED_BLOCKED_COMMANDS` | 原有项保留 + 追加 `spec.action_commands` | 8 号坑消失 |
| `TASK_STATUS` | `{spec.key: spec.status for spec in CATALOG.values() if spec.proxy_mode == "task"}` | 只能收 `task` 档，见 3.1 |
| `TASK_NAMES` | `proxy_mode in ("task", "config")` 的项 + **手写 `{farm: "灵田", fertilize: "施肥"}`** | 见下方警告 |
| 各 `_schedule_*` | 统一调度器读 `tick_interval` / `due_mode` / `settle_owner` | 见 3.8 |

> **警告：`TASK_NAMES` 不能纯派生。** 现有 6 项里 `farm` / `fertilize` 是维护动作（不占槽、不进 `user_cd`），按 3.6 不进目录。纯派生会让它们从表里消失，而 `TASK_ALIASES` 仍能把「灵田」「施肥」解析成对应 key —— 结果是**能开启、能跑，但所有拼文案的地方露出英文 key**（`_process_one` 的 `keep_text` 直接拿 `TASK_NAMES` 拼）。这类退化不报错，手测极易漏掉。

`TASK_ALIASES`（中文别名：「运镖」「历炼」…）同样无法派生，保留手写，放在目录同文件注释区。

### 3.4 白名单：只做追加，不做替换

首版说「手写只读/收益类 + 目录派生退出类」，方向对但没给清单。`BUSY_STATE_ALLOWED_COMMANDS` 现在约 90 项，其中真正属于「活动退出」的只有十余项，其余包括：

| 类别 | 例子 | 能否从目录派生 |
|---|---|---|
| 只读查询 | 我的信息、储物戒、丹阁、仙市、行情…（60+ 条） | 否 |
| 社交回应 | 接受双修、拒绝双修、接受切磋、拒绝切磋 | 否 |
| 代理管理 | 自动代理、关闭代理、代理状态 | 否 |
| 恢复类 | 调息、收功、服用丹药 | 否 |
| 通用解卡 | 解卡 | 否 |
| 无状态对应 | 完成悬赏、放弃悬赏、领取任务奖励、放弃任务 | 否 |
| 查询自身 | 押镖（进行中要能查状态） | 否 |
| 全服事件 | 魔潮状态、抵御魔潮 | 否 |
| 周本 | 周本离开、周本取消 | 否 |

**落地纪律：S2 只追加，不删除任何现有条目。** 新增活动不会漏退出指令（目录驱动追加），而原有 90 项一条不动，卡死风险为零。等 S2 跑一段时间确认稳定，再单独做一轮「收敛旧条目」。

这一条把 S2 的风险从「中」降到「低」，代价是白名单暂时保留冗余项——冗余项不影响正确性（`_is_command_allowed` 是遍历匹配）。

### 3.5 派生时的四条硬约束

1. **类型不能混**：`BUSY_STATE_ALLOWED_COMMANDS` 是 `list`（`_is_command_allowed` 遍历、支持 `startswith(cmd + " ")`），`BUSY_BYPASS_COMMANDS` 是 `tuple`（`command_text.startswith(...)` 直接传给它）。派生时把 list 塞进 `startswith` 会 TypeError。
2. **必须先追加再重建 tuple**：
   ```python
   BUSY_BYPASS_COMMANDS = tuple(dict.fromkeys(
       (*_BYPASS_HANDWRITTEN, *(c for s in CATALOG.values() for c in s.exit_commands))
   ))
   ```
3. **退出指令不能互为前缀**：`BUSY_BYPASS_COMMANDS` 走 `startswith` 宽匹配，现有「放弃任务」已会放行「放弃任务XXX」。如果新活动的退出指令取短词（如「结束」），会把「结束拍卖」之类全放过去。目录构建时应断言：任一 `exit_command` 不是另一条指令的前缀。
4. **现有列表本身有重复**：「完成历练」「完成悬赏」「完成探索」「丹药背包」「放弃任务」各出现两次。派生拼接后更多。若加「无重复」断言会直接失败，所以重建时统一走 `dict.fromkeys` 去重（顺序无关，遍历匹配不受影响）。

构建后要加的断言（S2 的测试）：

```python
for spec in CATALOG.values():
    for cmd in spec.exit_commands:
        assert cmd in BUSY_STATE_ALLOWED_COMMANDS      # list，用 in
        assert cmd in BUSY_BYPASS_COMMANDS             # tuple，用 in
    for cmd in spec.action_commands:
        assert cmd in INJURED_BLOCKED_COMMANDS

# 注意：**不能**断言 BYPASS ⊆ ALLOWED —— 这是首版的错误。现有「周本离开」
# 「周本取消」就在 BYPASS 里却不在 ALLOWED 里（BYPASS 走 bypass_busy 直接跳过
# 判定，不需要在 ALLOWED 中出现）。正确写法是钉住这条既有差集，防止它扩大：
assert set(BUSY_BYPASS_COMMANDS) - set(BUSY_STATE_ALLOWED_COMMANDS) == {"周本离开", "周本取消"}
```

### 3.6 边界：什么**不**进目录

避免过度设计，明确两类不进来：

- **维护动作**：施肥、灵田、坊市补货 —— 不占槽位、不进 `user_cd`，归 auto_proxy 的 `config_json` 管。
- **瞬时杂务**：炼丹、逛坊市、服用丹药 —— 瞬间完成，不占槽，但受「有没有空闲分身」约束（`player_required` 已处理）。

目录只描述**占槽的耗时活动**。这也是 `TASK_NAMES` 必须保留两个手写例外的原因。

### 3.7 `exclusive` 是死字段，别写进目录

首版 `ActivitySpec` 有 `exclusive: bool = True`，看起来可配，但 `start_activity` 的唯一性检查是：

```python
existing = await self.get_active_cd(user_id, cd_type)   # database_extended.py:523
if existing is not None:
    return False, int(existing.slot), "already_running"
```

**它根本不读这个字段。** 写成 `False` 不会有任何效果，只会误导后来人以为改一行就能多开。

要么在 S2 真接上（需要改 `start_activity` 签名、把唯一性约束从 `type` 改成 `(type, extra_key)`、加索引），要么删掉字段只留注释。当前建议：**删掉字段**，同类型多开作为独立议题（见第六节第 1 条）。

### 3.8 统一结算调度器

> S2 的 `ActivitySpec` 里**没有** `settle_owner` / `tick_interval` / `due_mode`——
> 那三个字段等 S4 真接调度器时再加，不要提前放进来（首版的 `exclusive` 就是前车之鉴：
> 字段看着能配，实际没人读）。

```python
async def _schedule_activity_settle(self):
    next_due = {st: 0 for st in CATALOG}
    while True:
        await self.db.ensure_connection()          # 保留：断连恢复
        now = int(time.time())
        for status, spec in CATALOG.items():
            tick = TICKS.get(status)
            if spec.settle_owner != "scheduler" or not tick:
                continue
            if now < next_due[status]:
                continue                            # 各 spec 独立计时，不互相拖
            next_due[status] = now + spec.tick_interval
            try:
                user_ids = await self._scan_due(spec, now)
            except Exception as e:
                logger.error(f"【结算】{spec.key} 扫描失败: {e}")
                continue                            # ← 单 spec 隔离，不影响其他活动
            for user_id in user_ids:
                try:
                    async with get_player_lock(user_id):
                        msgs = await tick(user_id)
                except Exception as e:
                    logger.warning(f"【结算】{spec.key}/{user_id} 失败: {e}")
                    continue
                for msg in msgs:
                    try:
                        await self._push(user_id, msg)
                    except Exception as e:
                        logger.warning(f"【结算】{spec.key}/{user_id} 推送失败: {e}")
        await asyncio.sleep(5)
```

三处必须守住的设计点：

**① 每个 spec 独立 try + 独立计时。** 现有 18 个循环各自有 `ensure_connection()` + 指数退避；合并成一个后，任一 spec 抛异常若不被隔离，整个循环进入退避，**其他活动一起停结算**。这是集中化最大的代价，必须用 `try` 逐个包住，并且按 spec 分别记 `next_due`，否则加了 `tick_interval=5` 的活动会把秘境拖成每 5 秒全表扫。

**② `tick` 必须是适配器，不能直接绑 manager 方法。** 两个现有结算函数的签名都对不上：

| 现有函数 | 返回 | 缺什么 |
|---|---|---|
| `adventure_mgr.finish_adventure(user_id)` | `(success, msg, reward_data)` | `_apply_adventure_rewards_meta`（悬赏/任务/称号）、从 `extra_data` 取 `umo`、`_send_to_origin` |
| `rift_mgr.settle_due(user_id)` | `{"messages": [...], "final": ...}` | `_apply_rift_rewards_meta`、`umo`、推送 |

所以 tick 契约统一成 `async (user_id) -> list[str]`，由 `main.py` 写两个适配器，把「结算 + meta 加成 + 取 umo 推送」整段包进去。首版示例 `bind_tick(EXPLORING, self.rift_mgr.settle_due)` 直接照抄会立刻崩。

**③ 秘境不能套用「到点结算」。** 它是每 5 分钟推进一段、`settle_due` 自己补算，所以目录里留 `due_mode="always"`，每次全扫 `type=EXPLORING`，由活动自己判断该补哪段。这点如果没分开，S4 一上线秘境就停止分段推送。

押镖 / 宗门任务保持 `settle_owner="auto_proxy"`，调度器跳过。等 S4 稳定后再评估是否收编。

## 十、后续补记：手动闭关与代理闭关分权（v4.0.6）

身外化身普及后，「本体手动 `/闭关` + 分身跑历练代理」是最常见的组合，但代理与手动闭关共用
`UserStatus.CULTIVATING` 一个槽位类型，且 `players.cultivation_start_time` 是玩家级单字段：

- `_start_adv_seclusion` 原来把 `start_activity` 的 `already_running` 当成「已接管」，
  随后无条件 `cultivation_start_time = now`，会把玩家已经修了多久清零；
- `close_until` 到点、`/关闭代理 历练`、切换到押镖/宗门任务时，又会按 `CULTIVATING`
  直接调用 `settle_cultivation`，替玩家手动出关。

改法（v4.0.6）：

- 代理开会话闭关时在 `user_cd.extra_data` 写入 `{"auto_proxy": "adventure_seclusion"}`；
  `AutoProxyManager._is_adv_seclusion()` 是唯一归属判定。
- `_start_adv_seclusion` 遇到无标记的 `CULTIVATING` 一律视为玩家手动闭关：不接管、不重置
  `cultivation_start_time`，返回 `manual_cultivation` 提示，等玩家出关后再决定是否自己闭关。
- `_settle_adv_seclusion` / `_settle_auto_seclusion_if_any` / `_run_adventure_cycle` 的
  `close_until` 分支、`/代理状态` 的「CD 自动闭关」文案全部加归属校验。
- 旧数据里没有标记的闭关一律按手动处理：宁可让玩家自己 `/出关`，也不代结算。

验收口径：手动闭关期间开历练代理，`cultivation_start_time` 不变、`close_until` 不被置位；
玩家出关后若路线仍在 CD，代理才自己开闭关；残留 `close_until` 也不会结算手动闭关。
